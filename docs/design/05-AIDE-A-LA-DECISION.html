PARTIE I — Gouvernance du versionnement des livrables UX/UI

I.1 Besoins à couvrir

Conserver l'historique complet · repérer les évolutions · comparer deux versions · revenir en arrière · tracer pourquoi une décision de design a été prise.

I.2 Les options

Option A — Versionnement simple par dossiers

Copies datées : design_v1/, design_v2_final/, design_v2_final_corrigé/…
AvantagesAucun outil ; compréhensible par tous ; retour en arrière = rouvrir un dossier
InconvénientsDuplication massive ; aucune différence lisible entre versions ; noms ambigus (« final2 ») ; décisions non reliées aux changements ; dérive entre copies
ComplexitéTrès faible au départ, croissante (le désordre augmente avec le temps)
Adaptation au projetFaible : le dépôt Git fournit déjà un historique gratuit ; refaire des copies à la main serait régressif

Option B — Versionnement par releases

Un numéro de version (v1.0, v1.1) et un instantané figé à chaque jalon validé (étiquette Git + archive des livrables).
AvantagesJalons nets, traçables ; retour en arrière précis ; langage commun (« version 1.2 validée »)
InconvénientsEntre deux releases, l'historique fin n'est pas rattaché aux décisions ; sans convention, les numéros perdent leur sens
ComplexitéFaible à moyenne
Adaptation au projetBonne : cohérent avec vos validations (« Je valide Sx ») et les étiquettes déjà posées par sprint

Option C — Versionnement de type Design System

Semver du système (MAJOR rupture · MINOR ajout · PATCH correction), journal des modifications par composant, jetons versionnés, dépréciations annoncées, décisions de design consignées (Design Decision Records).
AvantagesRigueur maximale ; compatibilité et dépréciations maîtrisées ; excellent pour de nombreuses équipes et plusieurs produits
InconvénientsLourd pour une équipe de deux ; surcoût de rédaction ; utile surtout quand plusieurs équipes consomment le système
ComplexitéÉlevée
Adaptation au projetMoyenne : on y viendra avec l'ERP (deux produits consommateurs) ; en faire trop maintenant ralentirait

Option D — Approche recommandée : Git comme source de vérité + releases sémantiques + journal de décisions légers

Combine le meilleur de B et C sans la charge de C :

  1. Git garde tout l'historique ligne à ligne (aucune copie de dossiers).
  2. Releases : à chaque validation, une version sémantique design-vMAJEUR.MINEUR.CORRECTIF (étiquette Git) et un instantané visuel des écrans.
  3. Journal des modifications unique (CHANGELOG-DESIGN.md) rédigé pour des humains.
  4. Registre des décisions de design (DDR) : une fiche courte par décision, reliée aux exigences EXD et aux versions.
  5. Comparaison visuelle par une page « avant / après » générée à partir de deux instantanés.
AvantagesHistorique complet, comparaison, retour arrière en une commande, traçabilité des pourquoi ; charge faible (le gros du travail est automatisable) ; évolue vers l'option C sans migration
InconvénientsDemande de la discipline (tenir le journal et les fiches) ; les instantanés visuels pèsent dans le dépôt (≈ 3 Mo par version à 18 captures : acceptable jusqu'à une trentaine de versions, au-delà on les sort du dépôt)
ComplexitéFaible à moyenne
Adaptation au projetTrès bonne : réutilise Git, les étiquettes, vos validations et le registre existant

PARTIE II — ARBITRAGE 1 : Navigation globale

Contexte

EXD-05 demande que la navigation complète n'apparaisse que dans « Vue d'ensemble », devenue hub et moteur de recherche global. Question : comment l'interpréter, avec quelles conséquences sur la productivité et le mobile ? Déjà acquis : recherche globale, modules dans une barre latérale pour l'instant, thème clair et sombre.

Option A — Navigation complète uniquement sur la vue d'ensemble

Ailleurs : aucune barre latérale ; fil d'Ariane et bouton « Vue d'ensemble ».
AvantagesPages de contenu épurées ; hub riche ; fidèle à la lettre d'EXD-05 ; peu de code de navigation
InconvénientsPasser d'un module à un autre impose de repasser par l'accueil ; dépend fortement de la recherche ; moins de repères
Impacts UXCharge mentale plus forte hors du hub ; bon pour la découverte, mauvais pour la répétition
Impacts mobilesNaturel sur téléphone (un écran = un contenu) mais sans accès rapide aux modules
Impacts productivitéNégatifs : +1 à +2 clics par changement de module ; pour un chargé de compte qui alterne agenda, entreprises, opportunités 30 fois par jour, c'est un coût réel (H)
Impacts techniques / maintenanceFaibles ; mais un module oublié dans le hub devient introuvable
AccessibilitéExige plusieurs moyens de navigation (WCAG 2.4.5) : la recherche seule ne suffit pas
Réversibilité🟢

Option B — Hub principal + rail compact (proposition actuelle)

Hub : navigation complète. Autres pages : rail d'icônes (72 px) avec info-bulles, « ← Vue d'ensemble », sous-navigation du module, recherche ⌘K.
AvantagesNavigation toujours à un clic ; contenu large ; garde l'esprit d'EXD-05 (la navigation détaillée est au hub)
InconvénientsIcônes seules : apprentissage nécessaire ; deux états de navigation à maintenir ; icônes à bien choisir
Impacts UXBon compromis ; risque de confusion pour les nouveaux utilisateurs sur la signification des icônes
Impacts mobilesRail remplacé par un tiroir ; cohérent
Impacts productivitéQuasi neutres par rapport à la barre complète
Impacts techniques / maintenanceMoyens : deux modes de coque, test de focus et d'info-bulles accessibles
Réversibilité🟢

Option C — Barre latérale pliable au choix de l'utilisateur (alternative pertinente)

Barre complète partout par défaut ; bouton pour la plier en rail ; la préférence est mémorisée ; le hub reste la page d'accueil enrichie.
AvantagesStandard éprouvé (outils de travail modernes) ; chacun choisit ; pas d'apprentissage imposé ; un seul composant
InconvénientsS'écarte de la lettre d'EXD-05 (la navigation complète est visible partout par défaut) ; les pages sont moins « épurées » par défaut
Impacts UXTrès bons ; efficacité maximale pour les usages répétitifs
Impacts mobilesTiroir ; identique à B
Impacts productivitéPositifs
Impacts techniques / maintenanceFaibles : un seul composant à deux états
Réversibilité🟢

Variante recommandée « B+ » (hybride de B et C)

Comme B (rail compact par défaut hors du hub, navigation complète au hub), avec un bouton « Déplier » qui montre la navigation complète partout, préférence mémorisée. Cela respecte EXD-05 par défaut tout en laissant la main à l'utilisateur.

PARTIE III — ARBITRAGE 2 : Module Opportunités

Contexte

Ancienne vue : colonnes par étapes (kanban). EXD-04 : cartes en lignes de 6, groupes empilés. Processus Investally (vérifié) : cycle B2B long ; étapes Prospection → RDV décideur → Offre → Accord de principe → Agrément → Inscrit Investudy ; règle « RDV décideur avant accord de principe » (dérogation tracée) ; plusieurs opportunités par entreprise ; ≈ 20 utilisateurs, quelques dizaines à une centaine d'opportunités actives (H).

Version actuelle — Vue en colonnes par étapes
LisibilitéExcellente pour où en est le portefeuille ; difficile de comparer des montants entre colonnes
ScalabilitéMoyenne : une colonne chargée devient longue ; au-delà de ~40 cartes, il faut filtrer
UXNaturelle pour faire avancer (glisser d'une étape à l'autre) ; l'étape est visible sans lire
Performance commercialeRévèle les goulots (trop de cartes en « Offre envoyée ») ; moins adaptée au tri par échéance
Pertinence InvestallyForte pour le suivi du processus et des règles d'étape ; faible pour comparer les montants
Impacts techniques / maintenanceGlisser-déposer à rendre accessible au clavier (coût)

Nouvelle version — Cartes en lignes de 6
LisibilitéForte pour comparer (montants, responsables, prochaines actions) ; l'étape devient une étiquette (moins immédiate)
ScalabilitéBonne jusqu'à ~60 cartes (10 lignes) ; au-delà : pagination, regroupement ou filtres
UXExploite bien la largeur d'écran ; sélection multiple et actions en lot naturelles ; peu adaptée pour faire avancer d'étape (menu ou fiche)
Performance commercialeBonne pour prioriser (tri par échéance ou montant) ; masque les goulots
Pertinence InvestallyBonne pour la revue d'équipe ; moins pour le suivi des étapes réglementées (règle du RDV décideur moins visible)
Impacts techniques / maintenancePlus simple (pas de glisser-déposer) ; tri et filtres indispensables

Version hybride — Une seule liste de données, deux présentations + bandeau d'étapes

Trois composants combinables :

  1. Bandeau de synthèse au-dessus : une pastille par étape avec son nombre et son montant ; un clic filtre (donne la vision « goulots » du kanban).
  2. Cartes par lignes de 6 (par défaut, comme demandé), triables (prochaine action, montant, étape).
  3. Bascule « Par étape » (colonnes) pour faire avancer les opportunités ; la préférence est mémorisée.
LisibilitéLa plus forte : synthèse + comparaison
ScalabilitéBonne : le bandeau et les filtres absorbent la croissance
UXChaque tâche a sa vue ; léger risque de choix à faire pour l'utilisateur
Performance commercialeMeilleure : priorisation et détection des goulots
Pertinence InvestallyTrès forte : respecte votre exigence, rend visibles les étapes réglementées
Impacts techniques / maintenanceMoyens : un seul modèle de données, deux rendus ; le prototype fait déjà la bascule

PARTIE IV — ARBITRAGE 3 : Module Stocks

Contexte

Approvisionnements internes d'Investally : articles, catégories, fournisseurs, entrées, sorties, inventaire, seuils, consommations internes. Faits : aucune relation avec les clients ni les opportunités ; tous les employés peuvent consommer, un petit nombre gère ; ADR-0005 sépare CRM et ERP (une base par produit, événements, aucun paquet partagé avant l'ERP) ; l'ERP n'existe pas encore, son socle (identité unique, paquets partagés) est à construire.

Option 1 — Stocks intégrés au CRM
AvantagesLe plus rapide : identité, droits, audit, interface et recette existent ; livrable en quelques sprints
InconvénientsPollue le périmètre du CRM (clients, pipeline, formation) ; contredit l'esprit d'ADR-0005 ; couple les cycles de livraison ; migration future coûteuse
Impacts métierLes stocks se retrouvent dans un outil « commercial » ; incohérence pour la finance (valorisation, achats)
Impacts techniquesSchéma dans la base du CRM ; migration vers l'ERP à prévoir (🔴)
Impacts organisationnelsPropriétaire flou ; droits Stocks mêlés aux rôles commerciaux
Impacts maintenanceDette de déménagement certaine
Réversibilité🔴

Option 2 — Stocks intégrés à l'ERP
AvantagesCohérence métier : « Opérations » (achats, finance, stocks) au même endroit ; respecte ADR-0005 ; pas de déménagement
InconvénientsAttend l'ERP (socle d'identité, paquets partagés) : plusieurs sprints avant la première ligne de stock ; risque de ne jamais commencer
Impacts métierBesoin réel (approvisionnement interne) satisfait tard
Impacts techniquesPropre, mais dépend de chantiers non commencés
Impacts organisationnelsResponsable naturel : opérations / finance
Impacts maintenanceFaible une fois posé
Réversibilité🟡

Option 3 — Module indépendant partagé

Un contexte stock autonome, utilisable par le CRM comme par l'ERP.
AvantagesDécouplé ; réutilisable ; évolue vers un service
InconvénientsSi on en fait un service séparé dès maintenant : déploiement, authentification inter-services, observabilité… disproportionné pour 20 utilisateurs
Impacts métierBon si le besoin dépasse un produit (H : c'est probable)
Impacts techniquesLourds s'il est déployé à part ; légers s'il reste un module
Impacts organisationnelsPropriétaire explicite
Impacts maintenanceMoyens
Réversibilité🟡

Variante recommandée « 3′ » — Module autonome, hébergé dans le monolithe du CRM, conçu pour être extrait

Un contexte stock avec son propre schéma (stock), aucune dépendance vers les modules du CRM (uniquement l'identité, l'audit et les droits via leurs interfaces publiques), échanges par événements, interface en section « Opérations » ; il s'extrait vers l'ERP (ou un service) sans réécriture quand l'ERP existera.
AvantagesLivrable tôt (socle réutilisé) et propre ; extraction planifiée ; respecte l'intention d'ADR-0005 (frontières nettes)
InconvénientsExige de la discipline de frontière (règles d'architecture automatiques déjà en place) ; un ADR dérogatoire doit documenter l'hébergement provisoire
Réversibilité🟢 à 🟡

Recommandation finale globale

En tant qu'architecte produit de la plateforme Investally, je choisirais la combinaison suivante : versionnement D, navigation B+, Opportunités hybrides, Stocks en module autonome (3′) et l'ordre alternatif 1. Pourquoi : c'est la combinaison qui protège ce qui est déjà solide (socle d'accès, règles d'architecture), livre la valeur commerciale le plus tôt possible sans coder deux fois, et garde chaque décision réversible. Les choix les plus coûteux à défaire (rattachement des Stocks, données de performance) sont traités avec des garde-fous explicites plutôt qu'avec de la vitesse. Le prochain geste utile n'est pas d'implémenter : c'est de valider S3.4 et S3.5 et de débloquer Microsoft 365 et les SuperAdmin.

Suite donnée le 2026-10-21 : la direction produit a demandé d'appliquer les décisions recommandées. Elles sont consignées dans le journal ci-dessous (annexe), dans QUESTIONS-ET-DECISIONS.md (D17), et appliquées : prototype v0.4.0, gouvernance du versionnement, ADR-0007, plan réordonné.
