Charger l'API du projet et la tester

La démarche complète, de zéro : installer, démarrer l'API sur votre poste avec des données de démonstration, puis la tester avec Postman (ou en ligne de commande), et vérifier la base de données. Compter une vingtaine de minutes la première fois.

Vue d'ensemble

Type d'API

REST en JSON sur HTTP (NestJS), décrite en OpenAPI 3. Adresses sous /api/v1.

Connexion

E-mail et mot de passe, puis un second facteur (code à 6 chiffres) : sans lui, les routes protégées refusent.

Ce que vous testez

180 routes : 373 requêtes et plus de 1 400 vérifications, dont des parcours qui créent leurs propres données.

Les fichiers utiles sont tous dans docs/api/ :

FichierÀ quoi il sert
postman/Investally-API.postman_collection.jsonLa collection de tests (JSON) : ce que Postman exécute. Une requête par route, avec ses tests.
postman/Investally-local.postman_environment.jsonL'environnement : adresse de l'API et identifiants du compte de test (à remplir, sans secret dans le fichier fourni).
tests-api.jsonLe catalogue des tests (JSON) : la même chose, lisible sans Postman : chaque route, sa permission, ses statuts attendus, la liste de ses tests.
openapi.jsonLa description OpenAPI de l'API, avec la permission de chaque route.
REFERENCE-DES-ROUTES.mdLa liste des routes par domaine.
README.mdLe guide de référence (conventions, erreurs, limites).

Ce qu'il vous faut

  • Node.js 22 et pnpm (pour démarrer le projet).
  • Postman (application de bureau ou web) ou Newman (npm install -g newman) pour la ligne de commande.
  • Une application d'authentification (TOTP) sur téléphone ou navigateur, ou la possibilité de copier la clé du second facteur (voir l'étape 2).
  • Le dépôt du projet : C:\dev\investally\investally-platform.
Important. Ne visez jamais une base de production avec ces tests : les parcours créent des données (préfixées « Postman »). Utilisez la pile locale ci-dessous, ou une pile jetable.

1. Démarrer l'API

  1. Se placer dans le projet et installer (une seule fois, puis après chaque mise à jour des dépendances).

    cd C:\dev\investally\investally-platform
git checkout main && git pull
pnpm install

  2. Démarrer la pile locale avec les données de démonstration. Elle lance PostgreSQL (port 54330), l'API (port 3001) et l'interface (port 3000), applique les migrations et charge un jeu de données fictives.

    node scripts/local-stack.mjs --demo --rebuild

    Ajoutez --rebuild après chaque mise à jour du code (il recompile). Sans lui, un redémarrage est rapide. Arrêt : Ctrl+C dans la console ; les données sont conservées.

  3. Vérifier que l'API répond.

    curl http://127.0.0.1:3001/health/live          # doit répondre 200
# Interface Swagger (toutes les routes, essai direct) :
#   http://127.0.0.1:3001/api/docs
    Bon signe : /health/live répond 200 et la page Swagger s'affiche.
Le premier démarrage compile tout et peut durer plusieurs minutes. Les mots de passe des comptes sont aléatoires : ils sont écrits dans C:\dev\investally\investally-local\demo-accounts.json (hors dépôt). Le mot de passe de l'administrateur admin@investally.test n'est affiché qu'une fois, au premier démarrage. Ne les copiez jamais dans un fichier du dépôt.

2. Préparer un compte de test

Prenez un compte qui a tous les droits : le Super administrateur (admin@investally.test). Les parcours de la collection touchent plusieurs domaines (commercial, formation, ressources humaines) : un compte plus limité aurait des refus (403 ou 404), que les tests acceptent mais qui rendent les parcours peu parlants.

  1. Noter l'e-mail et le mot de passe du compte (voir ci-dessus).

  2. Obtenir la clé du second facteur (mfaSecret). Deux façons, au choix :

    Par l'interface ouvrez http://127.0.0.1:3000, connectez-vous avec le compte. Au premier passage l'écran d'enrôlement affiche un QR code et la clé en texte : copiez cette clé (une suite de lettres et de chiffres), et scannez aussi le QR code avec votre application si vous voulez vous connecter à l'interface plus tard. Conservez les codes de secours.

    Par Postman si le compte n'a pas encore de second facteur, le dossier « 00b — Première connexion » le fait pour vous (étape 3) : le secret est conservé dans la variable mfaSecret.

    Le second facteur ne s'enrôle qu'une fois par compte. Si le compte est déjà enrôlé et que vous n'avez plus la clé, il faut la réinitialiser (droit d'administration), ou utiliser un autre compte.

3. Charger et lancer les tests dans Postman

  1. Importer. Postman › Import › glissez les deux fichiers de docs/api/postman/ : la collection « Investally Business Platform — API (tests) » et l'environnement « Investally — local ».

  2. Choisir l'environnement « Investally — local » (menu en haut à droite), puis ouvrir ses variables et renseigner :

    VariableValeur
    baseUrlhttp://127.0.0.1:3001 (déjà remplie : l'API locale)
    originhttp://127.0.0.1:3000 (déjà remplie : l'origine autorisée de l'interface)
    emaill'e-mail du compte de test
    passwordson mot de passe (type « secret »)
    mfaSecretla clé du second facteur (type « secret »)

    Enregistrez l'environnement (Ctrl+S). Les identifiants de ressources (companyId, etc.) sont déjà là, avec un identifiant inexistant : les parcours les remplissent.

  3. Se connecter. Dans la collection, dossier « 00 — Authentification » : lancez « 1 — Connexion » puis « 2 — Vérifier le code du second facteur ». Le code à 6 chiffres est calculé automatiquement à partir de mfaSecret : pas besoin de téléphone. Les deux requêtes doivent passer au vert, et le jeton est conservé pour toute la suite.

    Compte non enrôlé ? Lancez d'abord « 1 — Connexion », puis le dossier « 00b — Première connexion » (démarrer, puis confirmer) : il enrôle le second facteur et vous remet 10 codes de secours à conserver hors de Postman. Copiez ensuite le secret obtenu dans la variable mfaSecret de l'environnement.

  4. Lancer les tests. Deux façons :

    Tout clic droit sur la collection › Run collection › décochez « 00b » et « 98 » › Run. Durée : environ 40 secondes.

    Un dossier clic droit sur un dossier › Run folder, par exemple « 90 — Parcours de bout en bout » ou « 16 — companies ».

Ce que contient la collection

DossierCe qu'il faitCe qui est vérifié
00 — AuthentificationConnexion, second facteurJeton remis et vérifié
00b — Première connexionEnrôler le second facteur d'un compte neufSecret et 10 codes de secours remis
01 — Sécurité (173)Chaque route protégée, sans jetonRefusée (401), au format RFC 7807
02 — Santé/health/live, /health/ready200
90 — Parcours24 étapes qui créent leurs données : entreprise, formation (dont étudiant sans entreprise et payeur), congésStatuts, valeurs métier, refus de validation attendus
10 à 34 — par domaine (172)Une requête par routePas d'erreur serveur, jeton accepté, statut prévu, temps de réponse, JSON, erreur RFC 7807, champs documentés, pagination
98 — Actions de sessionDéconnexion, mot de passe, rafraîchissement, second facteurÀ lancer à part : elles ferment la session ou changent un secret
Ordre. Les parcours (90) passent avant les requêtes de route : ils enregistrent les identifiants qu'ils créent, que les requêtes de route réutilisent pour viser de vrais objets. Une route visée avec un identifiant inexistant répond « introuvable » (404) : c'est normal et accepté, cela prouve que la route existe, que le jeton est valide et que la portée est contrôlée.

4. Les lancer en ligne de commande

Pour rejouer les tests sans ouvrir Postman (par exemple avant une livraison) :

  1. Installer Newman (une fois) : npm install -g newman

  2. Préparer un environnement avec vos identifiants. Copiez docs/api/postman/Investally-local.postman_environment.json hors du dépôt (par exemple C:\dev\investally\investally-local\env-tests.json) et renseignez email, password et mfaSecret.

  3. Lancer.

    node scripts/api-docs/run-newman.mjs --env C:\dev\investally\investally-local\env-tests.json --report rapport.json

    La commande saute automatiquement les dossiers « 00b » et « 98 ». Options : --only 00,01,90 pour ne lancer que certains dossiers. Code de sortie 0 si tout passe, 1 sinon.

Résultat de référence (pile jetable, jeu de démonstration, Super administrateur) : 373 requêtes, 1 412 vérifications, 0 échec, en 40 secondes.

5. Tester la base de données

Postman ne sait pas interroger une base de données : le test de la base se fait avec un script en lecture seule, qui lance 22 vérifications d'intégrité (références entre domaines, places et agréments, chevauchement d'absences, comptes sans rôle…). Chacune doit renvoyer zéro ligne.

# Base locale : utilisateur investally_local, base investally_local, port 54330 ;
# le mot de passe (dbPassword) est dans C:\dev\investally\investally-local\secrets.json
$env:DATABASE_URL = "postgresql://investally_local:<dbPassword>@127.0.0.1:54330/investally_local"    # PowerShell
node scripts/db-docs/run-verifications.mjs

Sans Node : psql "$DATABASE_URL" -f docs/base-de-donnees/verifications.sql (chaque résultat non vide est une anomalie). Le dictionnaire complet de la base est dans docs/base-de-donnees/DICTIONNAIRE.md.

Résultat de référence : 22 / 22 vérifications réussies sur la pile de démonstration.

Ce que vous voyezCe que cela veut dire
Tout est vertLes routes répondent comme documenté : pas d'erreur serveur, jeton accepté, format d'erreur correct, règles des parcours respectées.
401 dans « 01 — Sécurité »Normal : c'est le résultat attendu (la route refuse l'appel sans jeton).
404 sur une route avec un identifiantNormal pour un identifiant inexistant : « introuvable ». Les parcours (90) créent de vrais objets, que les requêtes suivantes réutilisent.
400 sur une route de créationNormal : la requête de route envoie volontairement un corps vide, pour vérifier que la validation refuse sans rien créer.
Un test « Le jeton est accepté » en rougeProblème d'authentification : jeton absent, expiré, ou session fermée (par exemple après « 98 »). Relancez « 00 ».
Un test « Pas d'erreur serveur » en rougeUn vrai défaut de l'API (statut 500). Notez la route et le corps envoyé.

Le catalogue tests-api.json liste, pour chaque route, quels tests sont attendus : utile pour savoir ce qu'un test rouge contrôle.

8. Régénérer après un changement

La collection et le catalogue ne s'écrivent jamais à la main : ils sont produits depuis le code, pour ne pas dériver. Après l'ajout ou la modification d'une route :

cd apps\api
npx tsc -p tsconfig.build.json --outDir dist-docs
cd ..\..
# DATABASE_URL : une base JETABLE migrée (par exemple lancée par « node apps/api/scripts/test-db.mjs --keep »)
node scripts/api-docs/export-openapi.cjs --dist apps/api/dist-docs --out docs/api/openapi.json
node scripts/api-docs/build-postman.mjs

La dernière commande réécrit la collection, l'environnement, tests-api.json et la référence des routes. Elle échoue si un parcours vise une route qui n'existe plus : une dérive ne passe pas inaperçue.

Ce que ces tests ne couvrent pas

  • Les droits par rôle : la collection tourne avec un seul compte. La matrice des permissions est vérifiée par les tests automatiques du projet (roles.spec, contrat anti-accès croisé, tests d'intégration). Pour essayer un autre rôle, changez les trois variables du compte : les routes refusées répondent 403 ou 404, que les tests acceptent.
  • L'envoi de fichiers (documents, pièces jointes) : testé avec un corps vide ; un envoi réel se fait à la main.
  • Les valeurs exactes des réponses hors parcours : on contrôle la forme (statut, JSON, champs), pas chaque valeur.
