Réserves, limites et dette connues

  • Confusion undefined / null dans ma règle de décision de S2 : un objet existant sans propriétaire était traité comme une simple liste, donc accessible aux portées Propre et Équipe. Repéré avant d'écrire le code métier, corrigé et testé (le test échoue si on remet l'ancienne règle).
  • Route trop permissive détectée par la matrice : la Direction détient iam.session.revoke en portée « propre » et franchissait donc la garde de « révoquer toutes les sessions d'un autre utilisateur », avant d'être refusée plus loin avec un message flou. Ajout de minScope à @Protected : cette route exige désormais la portée Tous dès la garde.
  • Invitation sans step-up ni droit d'attribution (revue) : voir ci-dessus.
  • Violations d'architecture détectées par le contrat : mes contrôleurs importaient le Domain directement ; les types ont été exposés par la couche Application.
  • Tests trop stricts ou erronés de ma part : seuil arbitraire du nombre de routes (28 réelles), attente d'une liste vide pour un rôle sans permission (la réponse correcte est 403), exigence qu'un rôle soit refusé sur des routes ouvertes à tous.
  • Anciens tests de S1 supposant des routes publiques : ils attendent maintenant 401, ce qui est précisément le comportement voulu.
  • Incident de procédure (mon outil de mutation) : deux mutants visaient le même fichier et la restauration a échoué à mi-chemin, laissant du code muté. Détecté immédiatement, réparé depuis Git, vérifié (aucun .orig, aucun marqueur de mutation, écart limité aux changements voulus), script corrigé. Aucune trace dans les livrables.
  • Pas de front : l'invitation est un lien dont la page n'existe qu'en S3.4. En développement, EMAIL_LOG_CONTENT=true affiche le lien dans la console.
  • Microsoft 365 jamais testé en réel (registre D9).
  • Modifier le responsable d'un utilisateur change qui voit quoi (portée Équipe) mais n'exige pas de step-up ; l'action est auditée. À décider.
  • Les entreprises créées avant S3.3 n'ont pas de propriétaire : seuls les rôles en portée Tous les voient. Il n'existe pas encore de moyen de leur en attribuer un (S4.1).
  • Pas de réattribution d'une entreprise à un autre propriétaire (S4.1) ; un salarié qui part garde « ses » entreprises tant qu'on ne les réattribue pas.
  • La portée Équipe inclut les subordonnés directs désactivés ou en attente, donc leurs entreprises restent visibles de leur responsable.
  • Durées de session des rôles privilégiés : un changement de rôle s'applique aux droits immédiatement, mais la durée absolue de session (12 h) ne change qu'au prochain renouvellement.
  • Droits relus à chaque requête (2 requêtes SQL) : sans cache, volontairement (révocation immédiate) ; largement suffisant pour ≈ 20 utilisateurs.
  • Pas de révocation explicite d'une invitation hors renvoi ou désactivation du compte.
  • Limitation de débit en mémoire, une seule instance (dette D8).
